02 / 05 Ключевые решения

Структура раздела «Компании»

Почему три режима, единая карточка и как это связано с существующим продуктом

Решение 1

Три режима верхнего уровня

Раздел построен на трёх режимах, а не на одной ленте:

  • Мои компании — только аккредитованные, рабочий ежедневный экран с лентой активности
  • Запросы — исходящие и входящие отдельно (разные действия: я жду / я решаю)
  • Поиск — холодный контур, компании без отношений

Отказанные компании скрыты фильтром внутри «Запросы → Исходящие» — нечастый кейс не должен отъедать место у активных сценариев.

Решение 2

Единая карточка с переменным составом

Компания проходит один путь через статусы. Пользователю важно видеть развитие отношений, а не смену сущности.

Не аккредитована → Запрос отправлен → Аккредитована
Не аккредитована → Запрос отправлен → Отказано
Контекст

Связь с существующим продуктом

Аккредитация у текущего продукта существует как фича, но размазана по разным разделам — «Журнал заявок на аккредитацию», кнопка «Досье» с проверкой благонадёжности, виджет клиентов УЛ КАРГО, настройка требований аккредитации в «Организациях». Предложенная структура — это сведение разрозненной логики в одну связную сущность с понятной моделью отношений.

Гипотеза H1

Блок совпадений как «общие знакомые»

В карточке выведен блок совпадений с профилем перевозчика — общие маршруты, тип груза, частота публикации. Гипотеза: такой «тёплый» сигнал повышает долю запросов, доходящих до аккредитации, вместо рассылки вслепую.

Логика карточки

  • Статус none → кнопка «Отправить запрос на аккредитацию»
  • Статус rejected → кнопка «Подать заявку повторно» (blocked, если дата в будущем)
  • Клик по карточке → переход на экран профиля
  • Сетка: repeat(auto-fill, minmax(320px, 1fr))

Фильтры

Поиск по названию + select-фильтры «Регион» и «Тип груза». Визуально рабочие, фильтруют по массиву none + rejected.

05 / 05 Компромиссы и планы

Что сделано, чего нет, что дальше

Компромиссы

Что осознанно не делалось

  • Визуальная прорисовка главного экрана и входящих запросов (IA прописана текстово)
  • Кейс с несколькими юрлицами у одного грузовладельца (edge case в описании, не в макете)
  • Инструментация для проверки гипотез (метрики сформулированы, план аналитики не развёрнут)
  • Глубокая проработка микрокопирайтинга для пустых состояний и ошибок
При большем времени

Что доработалось бы

  • Пользовательское тестирование с 3–5 логистами: «найди перевозчика» / «обработай запрос»
  • Оставшиеся экраны: главный + входящие запросы
  • Кейс с несколькими юрлицами до полноценного UI
  • Прозрачный статус-степпер с ориентировочным сроком ответа на основе истории компании
Гипотезы

Что проверяем

  • H1: Блок совпадений (общие маршруты/тип груза) повышает конверсию запросов в аккредитацию
  • H2: Разделение исходящих/входящих запросов снижает когнитивную нагрузку
  • H3: Прозрачный статус-степпер снижает количество повторных запросов от перевозчиков
